## 2. Decisiones (pins)

**D1 (D-1 del PREP) — Panic uniforme.** El desbordamiento de `+ - *` sobre Int no literal produce **PANIC UNIFORME** (exit 101, mensaje de rustc `attempt to add|subtract|multiply with overflow`) en **TODOS** los perfiles (`arita build` debug, `--profile release`, `arita test`). Se logra por perfil (opción O3b del PREP), **sin cambiar el Rust emitido**. **Q1 RESUELTA (Ingeniero, 2026-10-03): SÍ O3b** (D1/D2 confirmadas).

**D2 (D-2) — Mecanismo por perfil.** El `[profile.release]` del Cargo.toml emitido lleva `overflow-checks = true` (junto a `opt-level = 3`; LTO off) y `arita test` invoca `rustc --test -O -C overflow-checks=on`. **Hallazgo sobre workspaces (Q4, verificado por lectura de `crates/arita-cli/src/package.rs`):** los workspaces de package **no** usan `emit_cargo_toml_with_hosts`: el `Cargo.toml` raíz sale de `emit_workspace_cargo_toml` (L186–L200, escrito en L300–L303) y solo contiene `[workspace]`, `resolver` y `members`; los `Cargo.toml` de cada miembro (L375 y L460) llevan `[package]`, `edition = "2021"` y dependencias; **ningún** `[profile.*]` propio, tampoco `opt-level = 3`. Por tanto el cambio de `emit_cargo_toml_with_hosts` **no alcanza** a `arita build --profile release` sobre un package; para cumplir D1 también ahí, IMPL debe añadir el `[profile.release]` con `overflow-checks = true` al `Cargo.toml` raíz del workspace (cambio en `package.rs`: `emit_workspace_cargo_toml` hoy no recibe el perfil). [H: que Cargo solo aplica `[profile.*]` desde la raíz del workspace es comportamiento conocido de Cargo; no medido aquí.] El PREP (L123, L178) dejaba esto sin comprobar. **Q4 RESUELTA (Ingeniero, 2026-10-03): SÍ** — `[profile.release]` con `overflow-checks = true` en el `Cargo.toml` **RAÍZ** del workspace; `emit_workspace_cargo_toml` debe recibir/emitir el perfil. Se **MIDE en IMPL**; la afirmación sobre Cargo se mantiene como [H] hasta medir que Cargo aplica `[profile.*]` solo desde la raíz del workspace.

**D3 (D-3) — `/` y `%` no cambian.** El panic de Rust (div0, `MIN ÷ −1`) se mantiene y se documenta; E0216/E0217 como hoy.

**D4 (D-4) — `MIN / -1` literal-ligado.** Hoy sale como E0100 de rustc (PREP L63), no como E0217: ticket **B-292-1 (P3, HIR)**, fuera de este slice.

**D5 (D-5) — `known_int` no sensible al flujo.** El const-fold no es sensible al flujo: una asignación dentro de un `if` sobrescribe `known_int` y ese valor sobrevive fuera del bloque; **falso negativo medido** (PREP L77 y L153). Ticket **B-292-2 (P2, HIR)**, fuera de este slice. **HIPÓTESIS (no medida):** el mismo defecto podría producir un **falso positivo** de E0217 (p. ej. `let a = 0; if c { a = MAX }; a + 1`); HIR debe comprobarlo antes de decidir la severidad. **Q3 RESUELTA (Ingeniero, 2026-10-03):** B-292-2 sigue P2, pero HIR debe comprobar el falso positivo de E0217 **ANTES de v1**; si se confirma, **sube a P1** (sigue siendo hipótesis, no medida). **(→ ADR-294, P1; la etiqueta “hipótesis” queda superada: falso positivo MEDIDO por PREP_B292_2_20261004)**

**D6 (D-6) — Asimetría declarada y addendum de referencia.** `v[i] op= x` (ADR-290 D5-ii) ⇒ `Err(0)` sin panic; `a + b` ⇒ panic 101. La frase de ADR-290 «panic en debug, wrap en release» se **precisa** por esta vía (las tres rutas de §1) **sin reescribir ADR-290** (CLOSED): este ADR es el addendum de referencia. Se anota además como **enmienda de ADR-045 §OUT**: el «overflow no-lit complejo» pasa a tener contrato de runtime (D1).

**D7 (D-7) — Lints de clippy.** `clippy::assign_op_pattern` (4 ocurrencias) e `identity_op` (1) en 4 de 63 positivos emitidos hoy (PREP L98): **FUERA** de este slice. **Q2 RESUELTA (Ingeniero, 2026-10-03):** se redirige a **B-289-1 (P3)** (otros lints de rustc/clippy en positivos); **B-292-3 → B-289-1 (P3)**, sin entrada propia.

**D8 (D-8) — Sin enmienda de ADR-289 ni ADR-230.** No aplica enmendar ADR-289 (PU2, 10 tests de texto) ni ADR-230 porque el Rust emitido **no cambia** (O3b). Verificar y declarar al IMPL: 0 cambios en el texto emitido (PREP L139 y L143–L147).

**D9 — Opciones no adoptadas.** **O1** (`checked` + `?` en fns `-> Result<_, Int>`; 62 de 63 positivos dejarían de compilar sin cambiar los `.arita`, PREP L103) queda como feature de lenguaje opt-in para v2: **B-292-4 (P3)**. **O2** (wrapping), **O3a** (panic textual: choca con ADR-230 R0/R2, PREP L119) y **O4a** (saturating) **NO** se adoptan. **O4b** (solo documentar la dependencia del perfil) es el mínimo si el Ingeniero rechaza D1 (PREP L163).

**D10 — Cobertura de rutas.** **Toda ruta que compile Rust emitido debe llevar `overflow-checks`.** IMPL enumera y cubre, como mínimo: R1–R5 de §1 (`build` de fichero y de package, en debug y en release; `arita test`) y `arita run` **si existiera** (hoy no existe, §1). Las rutas debug por `rustc` sin `-O` (R1) y por Cargo `dev` (R2/R3 en debug) ya hacen panic hoy [V para R1, PREP L52; H para el perfil `dev` de Cargo, no medido]. IMPL debe además clasificar los arneses de `measure.rs` del hallazgo de §1 (cuáles construyen Rust emitido en release con un `Cargo.toml` propio) y reportar cualquier ruta nueva al Ingeniero antes de tocarla.

## 6. Riesgos

- El panic sigue siendo un canal de fallo no tipado (consistente con `/` `%`; el ideal «sin panic» queda para v2 / B-292-4).
- Cambio observable en release (wrap → panic) solo en programas que desbordarían (0 en el corpus, PREP L97).
- Coste de `overflow-checks` no medido (medición informativa en el GATE, §3).
- Los workspaces de package no heredan hoy ningún `[profile.release]` (D2): sin el cambio en `package.rs` (Q4 resuelta: SÍ), D1 no se cumpliría en `arita build --profile release` sobre un package; IA-4 lo cubre.
